# Настанови щодо розробки та внесення змін (Contribution Guide)
Дякуємо, що виявили інтерес до нашого десктопного застосунку To-Do! Цей
документ створено для сторонніх користувачів, контриб&#39;юторів та
розробників. Він описує чіткі правила гри, технічні стандарти та
регламенти, які допомагають підтримувати високу якість коду та
забезпечують стабільність функціонування проєкту.
Будь ласка, уважно ознайомтеся з цією інструкцією перед тим, як
пропонувати будь-які покращення чи відправляти зміни в репозиторій.
---
##  1. Як почати роботу з проєктом
Щоб розпочати роботу з вихідним кодом застосунку, виконайте такі кроки:
1. **Створіть Fork проєкту:** Перейдіть на сторінку репозиторію на GitHub
і натисніть кнопку **Fork** у верхньому правому кутку, щоб створити власну
незалежну копію проєкту у своєму акаунті.
2. **Клонуйте репозиторій локально:** Завантажте створений форк на свій
локальний комп&#39;ютер за допомогою Git клієнта або терміналу:
```bash
git clone https://github.com/ваш-юзернейм/SQE-lab2.git
cd SQE-lab2
```

##  2. Налаштування віртуального середовища
Для повної ізоляції залежностей проєкту від системних пакетів розробка має
вестися виключно всередині віртуального середовища (`venv`).
Переконайтеся, що у вас встановлено Python версії **3.10 або вище**.
### Створення та активація середовища (Windows)
* **через Command Prompt (CMD):**
```bash
python -m venv venv
.\venv\Scripts\activate
```

* **через PowerShell:**
```bash
python -m venv venv
.\venv\Scripts\activate.ps1
```
### Створення та активація середовища (Linux / macOS)
```bash
python -m venv venv
source venv/bin/activate
```
### Встановлення інструментів тестування
```bash
pip install pytest
```

##  3. Стандарти написання кодуCoding Standards)
Щоб кодова база залишалася чистою, структурованою та легкою для читання,
дотримуйтесь таких правил:
*  **Дотриманн PEP 8:** Весь новий код на Python має відповідати
офіційному посібнику зі стилю PEP 8 (використання відступів у 4 пробіли,
іменування функцій та змінних у стилі `snake_case`, класів — у стилі
`CamelCase`).
* **ому файлі чи методі. Розділяйте графічну частину Tkinter (GUI) від
логіки обробки та збереження файлів конфігурацій.
*  **Документування та коментарі:** Кожна нова функція, модуль або тест-
кейс повинні супроводжуватися коротким коментарем (`docstring`) або інлайн-
нотатками, що пояснюють бізнес-логіку написаного коду.

##  4. Обов&#39;язкове тестування кодуRunning Tests)
Якість та стабільність нашого застосунку повністю контролюються
автоматизованими тестами. **Жодна зміна не буде злита в головну гілку
(main), якщо вона ламає наявні тести або не покрита новими перевірками.**

Перед створенням коміту або надсиланням змін на GitHub обов&#39;язково
запустіть локальний тестовий набір через фреймворк `pytest`:
### Запуск усієї тестової збірки (Рекомендовано)
```bash
python -m pytest -v
```
### Поетапний запуск окремих тестів:
* **Перевірка базової графічної логіки через assert:**
```bash
python -m pytest test_assert.py
```
* **Перевірка розширеного набору тестів (фікстури та параметризація):**
```bash
python -m pytest test_pytest.py -v
```
* **Перевірка обробки критичних винятків та помилкових сценаріїв:**
```bash
python -m pytest test_raises.py -v
```
* **Моніторинг тимчасово пропущених функцій або відомих очікуваних
дефектів:**
```bash
python -m pytest test_skip.py test_xfail.py -v
```
&gt; ⚠️ **Увага:** Переконайтеся, що в кінцевому результаті термінал повертає
виключно зелений статус (`passed`). Якщо хоча б один тест падає
(`FAILED`), локалізуйте та виправте дефект перед фіксацією змін.

##  5. Регламент створення комітів т Pull Request
### Правила оформлення повідомлень комітів (Commit Messages)
Повідомлення мають бути лаконічними та чітко описувати суть змін за
семантичним принципом:
* `feat: ...` — додавання нового функціоналу (наприклад, `feat: add task
priority color markers`).

* `fix: ...` — виправлення виявленої помилки або багу (наприклад, `fix:
resolve crash on empty listbox deletion`).
* `docs: ...` — зміни в документації, інструкціях користувача або файлах
розмітки Markdown.
* `test: ...` — розробка нових модульних тестів чи виправлення існуючої
логіки перевірок.
### Алгоритм надсилання змін (Pull Request Workflow)
1. **Створення гілки:** Створіть нову робочу гілку від `main` із назвою,
що відповідає вашій задачі:
```bash
git checkout -b feature/назва-нової-фічі
```
2. **Локальна перевірка:** Внесіть зміни в код програми, детально
протестуйте їх локально через `pytest`.
3. **Пуш змін:** Зафіксуйте зміни у своїй гілці й відправте її на GitHub
через термінал або інтерфейс GitHub Desktop:
```bash
git push origin feature/назва-нової-фічі
```
4. **Оформлення PR:** Перейдіть у головний репозиторій проєкту та
відкрийте новий **Pull Request (PR)**. Детально опишіть, які саме проблеми
вирішує ваш код та додайте скриншоти, якщо ви змінювали графічний
інтерфейс Tkinter.
